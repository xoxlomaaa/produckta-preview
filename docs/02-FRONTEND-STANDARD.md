# Универсальный технический стандарт сайта

Версия 1.3 · 10.11.2026. Назначение: повторяемая архитектура кода для сайтов с разными сетками, CMS, дизайном и адаптацией.

## 1. Что стандартизируется

Общие правила определяют расположение кода, ответственность модулей, зависимости, обработку данных, жизненный цикл, сборку, подключение ресурсов и проверку.

Каждый проект отдельно определяет платформу, рендеринг, визуальные параметры, схему адаптации, условия переключений, масштабирование, эффекты, браузеры и бюджеты ресурсов. Для новых публичных сайтов стартовый подход — mobile-first CSS. Иной порядок адаптации допустим, когда его обосновывают существующий стек или макет. Конкретные пороги и контейнеры выбирает проект. Пример каскада и правила загрузки см. в [руководстве](05-PERFORMANCE-PLAYBOOK.md).

Решения записываются в профиль по [шаблону](templates/PROJECT-PROFILE.md). Это способ зафиксировать исходные условия, а не требование согласовывать каждую строку кода.

## 2. Слои и ответственность

| Слой | Ответственность |
|---|---|
| Маршрут / entry point | Выбор страницы и контекста вызова |
| Данные / сервисы / CMS adapter | Получение, проверка данных, бизнес-операции |
| View model / параметры шаблона | Подготовленные значения для представления |
| Layout / page / section / component | Сборка HTML из подготовленных данных |
| SCSS/CSS | Представление, состояния и адаптация |
| JavaScript | Поведение, состояние, клиентские запросы |
| Сборка | Преобразование исходников в публичный артефакт |
| Конфигурация окружения | Настройки среды и закрытые параметры интеграций |

Исходники отделяются от результата сборки и служебных материалов. Разметка не выполняет скрытые бизнес-операции, JS не становится вторым источником тех же данных, backend не зависит от декоративных CSS-классов.

Дерево из документа 03 — рекомендуемая организация. CMS/framework может задавать другое физическое расположение при сохранении понятных границ. PHP и имена папок референса не обязательны для каждого нового сайта.

## 3. Данные, конфигурация и HTML

- У повторяемых данных один определенный источник: CMS, конфигурация или файл контента. Не поддерживать разные версии контактов/названий в HTML, PHP и JS вручную.
- Layout владеет оболочкой документа, page — составом страницы, section — разделом, component — повторяемым самостоятельным фрагментом. Не выносить каждую обертку в отдельный файл без причины.
- Входные параметры компонента явные: поля, обязательность, значения по умолчанию. Не полагаться на случайные глобальные переменные шаблонизатора.
- Основной текст и ссылки индексируемой страницы доступны в исходном HTML/SSR/SSG. Для клиентского приложения другая модель рендеринга определяется требованиями маршрута.
- Использовать семантический HTML, корректные lang/encoding/viewport, заголовки и landmarks. Ссылка выполняет переход, кнопка — действие, поле имеет доступное имя.
- IDs уникальны; связи label/for и ARIA references существуют. Повторный экземпляр компонента получает собственные идентификаторы.
- Экранировать значения по контексту: HTML, атрибут, URL, JSON. Валидация входа не заменяет экранирование выхода.
- Публичную JS-конфигурацию формировать явным списком разрешенных полей. Не сериализовать всю серверную конфигурацию.
- Предусматривать базовый сценарий при ошибке JS. Для функций, которым JS необходим, определить состояние отказа и альтернативный путь, если он требуется продуктом.
- Правовые тексты, метаданные и бизнес-контент не переносятся из референса как часть технического шаблона.

## 4. SCSS/CSS и каскад

SCSS — исходный модульный слой, CSS — браузерный результат. Если SCSS не нужен, те же границы применимы к обычным CSS-модулям.

| Модуль | Содержимое |
|---|---|
| abstracts / tokens / config | Проектные значения, функции, mixins, именованные условия адаптации |
| base | Общие правила документа, нормализация, font-face, инфраструктура фокуса |
| layout | Реализация каркасов, выбранных для проекта |
| components | Стили компонентов и состояний |
| sections / pages | Локальные стили уникальных частей страниц |
| entries | Явный состав и порядок подключения стилей маршрута |
| utilities | Небольшие общие технические helpers |

Токены определяют место хранения значений, а не универсальные цвета, отступы, размеры или брейкпоинты.

1. Использовать явные зависимости; для SCSS — `@use`/`@forward`. Поддерживать одну понятную схему подключения внутри проекта.
2. Различать модули, предоставляющие переменные/mixins, и модули, выводящие CSS. Проверять отсутствие ненужной повторной генерации общих правил.
3. Каскад контролируется entry point. При использовании CSS layers их порядок согласован с внешними стилями.
4. Компонент владеет своими селекторами. Схема именования — BEM, CSS Modules или другая — выбирается проектом и применяется последовательно.
5. JS привязывается к стабильным hooks/props, а не к декоративным классам или позиции `nth-child` в макете.
6. Адаптивные правила находятся в модуле компонента либо в явно выделенном модуле его адаптации. Не распределять их по цепочке файлов исправлений.
7. Правку вносить в файл-владелец. Не наращивать `final-fix.css`, `mobile-fix-2.css` и специфичность вместо устранения причины.
8. Глобальные селекторы, `!important` и глубокая вложенность требуют понятной причины. Не использовать их для обхода неизвестного порядка каскада.
9. Интерактивные состояния имеют согласованное соответствие CSS ↔ DOM/ARIA ↔ JS: скрытие, блокировка, ошибка, загрузка.
10. Собранный CSS не редактируется вручную. От ресурса должен быть прослеживаемый путь к исходнику через entry/manifest/source map или документацию.

## 5. Техническая организация адаптации

Этот раздел определяет, как хранить и исполнять адаптивную логику. Он не задает сетку, ширины, типографику, набор порогов или модель масштабирования.

### Условия и владелец

- В профиле проекта описать, какие условия меняют представление, а какие — поведение: viewport, контейнер, ориентация, возможности указателя, пользовательские настройки.
- Общие условия хранить в конфигурации проекта; локальные могут принадлежать компоненту. Не заставлять все компоненты использовать один глобальный breakpoint без необходимости.
- Выбранный порядок media/container queries должен быть последовательным. Учитывать каскад при сочетании разных схем переопределений.
- CSS отвечает за представление. JS подключается к условию, если меняются функциональность, состояние, состав тяжелых модулей или управление ресурсами.
- Если условие нужно CSS и JS, определить общий источник либо механизм синхронизации. Не поддерживать расходящиеся значения вручную.
- Размер экрана, тип указателя и производительность — разные характеристики. Не делать вывод о возможностях устройства только по ширине или user-agent.

### Переключение работающей страницы

- Обрабатывать вход и выход из режима, а не только начальную загрузку. Resize, смена ориентации или размера контейнера оставляют компонент в согласованном состоянии.
- Использовать механизм по задаче: CSS queries для представления, `matchMedia` для условий поведения, `ResizeObserver` для размеров компонента. Не переинициализировать всю страницу на каждый resize.
- При перестройке сохранять пользовательские данные и значимое состояние. Закрытое меню не оставляет невидимый фокус; форма не теряет ввод из-за пересоздания DOM.
- Ресурсы предыдущего режима освобождаются, новые не накапливаются при повторных переключениях.
- Избегать независимых дубликатов одной бизнес-формы. Если разные DOM-ветки нужны проекту, определить общую модель данных, уникальные IDs, активную ветку и управление ресурсами каждой.
- Отдельные server-rendered варианты документировать вместе с маршрутизацией, кешированием и эквивалентностью данных. Не вводить это ветвление автоматически для всех сайтов.

### Загрузка по условиям

- Скрытие элемента CSS не считать гарантией отсутствия сетевого запроса или выполнения JS.
- `picture/srcset/sizes` согласовываются с реальными вариантами компонента. При изменении адаптации перепроверяется выбор файла браузером.
- Код отдельного режима может загружаться динамически. При смене режима учитывать отмену, уже загруженный модуль и отсутствие повторной инициализации.
- Проверять прямой вход, клиентскую навигацию, смену режима после взаимодействия и восстановление из истории.

Матрица проверок определяется конкретным проектом: его условия переключения, поддерживаемые устройства и способы ввода. Общая архитектура кода сохраняется при разных сетках и схемах адаптации.

## 6. JavaScript и lifecycle

У компонента определены root/props, зависимости, состояния, публичные методы/события и порядок уничтожения. Статичному фрагменту отдельный JS-компонент не нужен.

- Init проверяет необходимые узлы и безопасен при повторном вызове либо предотвращает повтор.
- Экземпляр имеет одного владельца: page registry, router или framework. Нет нескольких скрытых точек init того же DOM.
- Listeners, observers, timers, rAF, animation handles и requests учитываются и освобождаются.
- Destroy безопасен при повторном вызове. Временно измененные атрибуты и состояния восстанавливаются там, где DOM продолжит использоваться.
- Async-операция имеет сценарии успеха, ошибки и отмены. Поздний ответ не обновляет уничтоженный или заново открытый компонент.
- Ошибка независимого компонента не останавливает остальные. Ошибки наблюдаемы, но логи не раскрывают персональные данные и секреты.
- Общими ресурсами документа управляет общий сервис с явным владельцем: например, стек диалогов или scroll lock.
- Lifecycle учитывает router/CMS/framework и bfcache. Не считать каждое `pagehide` окончательным уничтожением.

Чтения layout и записи DOM группируются там, где это существенно. Частые события не запускают полную перестройку страницы. Class/function/framework выбираются проектом; универсальным остается контракт, а не конкретная иерархия классов из архива.

## 7. Интерактивные состояния и доступность

- Действия доступны предусмотренными способами ввода. Клавиатура и фокус не зависят от hover.
- Видимые, скрытые, заблокированные и активные состояния корректно отражаются в DOM и accessibility tree.
- Menu/tabs/select/dialog реализуют соответствующие управление клавиатурой и ARIA-связи. Использовать native controls, если они подходят по функции; custom control получает полный контракт поведения.
- Modal управляет initial focus, фоном, Tab/Escape, вложенными окнами и возвратом фокуса. Способ реализации выбирается проектом.
- URL, якоря, прямые ссылки и история согласованы с пользовательским сценарием. Изменение стандартного поведения — явная функция проекта, а не случайный побочный эффект.
- Пользовательские настройки, включая reduced motion, учитываются соответствующими компонентами. Альтернативное поведение определяется проектом.
- Эффекты имеют запуск, остановку, cleanup и обработку ошибки. Этот стандарт не назначает им траектории, длительности или внешний вид.

Контраст, размеры целей, reflow и другие параметры доступности проверяются по выбранному профилю соответствия. Они не подменяются типографической шкалой или сеткой, заимствованной у референса.

## 8. Формы, API, интеграции

До реализации определить endpoint, поля и ограничения, схему ответов, авторизацию/CSRF, anti-abuse, deadline, повторную отправку и смысл успеха.

- Клиентская валидация помогает пользователю; серверная проверка остается обязательной.
- Ошибки связаны с полями и сообщаются доступным способом. Введенные данные сохраняются при неуспехе, если нет объективной причины их удалить.
- Ожидание, отправка, успех, ошибка и отмена различаются. Повторное нажатие не создает неконтролируемые дубли запросов.
- Закрытие/destroy отменяет соответствующую работу; устаревший ответ игнорируется.
- HTTP status и схема тела ответа проверяются совместно. Завершившийся `fetch` сам по себе не означает успех операции.
- Сообщение успеха соответствует подтвержденному backend-событию: принятию, очереди или доставке.
- CAPTCHA, почта, платежи и CMS изолируются в adapters/services. Шаблон формы не содержит реализацию интеграции.
- Секреты находятся в окружении/secret store без действующих fallback в коде. Отсутствие настройки дает контролируемую ошибку.
- Серверные ограничения учитывают реальные прокси, сессии и количество инстансов.
- Внешний iframe/скрипт имеет состояния загрузки и отказа. Событие `load` не доказывает завершение бизнес-операции.
- При postMessage проверяются origin/source/схема. Права внешних интеграций соответствуют реальным потребностям.

## 9. Ресурсы и порядок загрузки

Поток: исходник → обработчик сборки → публичный файл → manifest → template/helper → запрос браузера.

### CSS и JS

- Страница получает нужные entry points; общие chunks выделяются по реальным зависимостям.
- Стратегия CSS — обычный stylesheet или critical/deferred — выбирается измерением. Инлайн большого CSS не становится обязательным приемом.
- Для deferred CSS проверяются порядок применения, CSP и базовое поведение при отказе соответствующего JS.
- Module/defer и dynamic import согласованы с зависимостями. Ненужные блокирующие scripts не попадают в критический путь.
- Дополнительные тяжелые модули и внешние сервисы загружаются по потребности. Основной индексируемый контент не откладывается до действия пользователя только ради экономии начального запроса.

### Медиа и шрифты

- Размеры/соотношения сторон ресурсов известны браузеру; загрузка не создает непреднамеренных сдвигов документа.
- `srcset` соответствует файлам, `sizes` — логике представления. Выбор проверяется в Network на целевых устройствах.
- Вероятный LCP-ресурс не получает lazy loading. Preload/priority применяются избирательно и проверяются на отсутствие дублей.
- Варианты ресурсов создаются воспроизводимо. Masters отделены от публичной поставки.
- Шрифты подключаются с учетом нужных диапазонов/начертаний, лицензии и fallback. Сами шрифты и их размеры выбираются дизайном проекта.

### Кеширование

- При изменении ресурса меняется его версия/URL. Предпочтителен manifest с content hash; другой механизм должен иметь понятные гарантии инвалидации.
- Immutable cache применяется к неизменяемым URL. HTML, сессии и персональные данные имеют отдельную политику.
- Публикация HTML и assets согласована; ранее открытая страница не теряет файлы сразу после релиза.
- Compression, MIME, cache headers и правила доступа проверяются на реальном сервере. Preview не подтверждает настройку hosting/CDN.

## 10. Сборка и техническая приемка

Runtime и зависимости фиксируются; lockfile хранится в репозитории. Чистая установка, build, preview и проверки описаны рабочими командами. Названия `dev/build/check/preview` — рекомендуемый контракт, а не заявление о наличии готовых scripts.

Сборка дает воспроизводимый публичный артефакт. В публикацию не попадают секреты, исходные архивы, отчеты, инструменты аудита и ненужные runtime зависимости. Source maps имеют явно выбранную политику доступа.

Проверяются синтаксис, зависимости, семантика HTML, данные, ресурсы, lifecycle, отмена запросов, смена адаптивных режимов, доступность состояний, fallback и реальный production build. Для индексируемых страниц проверяются HTTP-статусы, метаданные, canonical, robots и sitemap по [стандарту SEO и выпуска](06-SEO-AND-RELEASE.md).

Бюджеты HTML/CSS/JS/media, целевые метрики, браузеры и устройства устанавливаются в профиле проекта до масштабирования реализации. Первый сквозной сценарий проверяется на production build по [методике](05-PERFORMANCE-PLAYBOOK.md). Набор чисел предыдущего сайта не наследуется. Лабораторные измерения отделяются от production и field-данных; балл Lighthouse не гарантирует позиции в поиске или полную корректность интерфейса.

Объем проверки соответствует изменению. Регрессионные тесты добавляются для поведения с существенным риском ошибки; тесты, лишь повторяющие статическую разметку, не являются самоцелью. Отчет о завершении описывает изменение, выполненные проверки и ограничения.
