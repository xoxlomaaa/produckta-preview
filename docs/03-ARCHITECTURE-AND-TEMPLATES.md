# Архитектура и технические шаблоны

Версия 1.3. Документ описывает исходное дерево, связи и контракты. В нем нет готовой сетки, визуального компонента или заданных брейкпоинтов.

Структура предложена по результатам изучения production-поставки. Исходных SCSS/JS-модулей и сборщика в архиве не было, поэтому это не восстановленные исходники его автора.

## 1. Рекомендуемое дерево

```text
project/
├── AGENTS.md
├── README.md                    реальные команды запуска, сборки, проверки
├── package.json                 если используются Node build tools
├── package-lock.json            либо lockfile выбранного package manager
├── .env.example                 имена настроек, без действующих секретов
├── public/                      web root или эквивалентный output платформы
│   ├── index.*                  публичная точка входа
│   ├── api/                     публичные endpoints без бизнес-логики
│   └── assets/
│       ├── manifest.json        logical name → собранный versioned URL
│       ├── css/
```

Это схема ответственности, не требование создать все папки. Сайт без API не нуждается в пустом backend. CMS/framework сохраняет свою структуру: в README указывается, какие ее узлы соответствуют этим слоям. Исходники, секреты и отчеты отделяются от публичной области средствами выбранной платформы.

## 2. Кто что читает

| Узел | Вход | Выход | Граница |
|---|---|---|---|
| Router/entry | URL, контекст запроса | выбранная page и параметры | не содержит всю страницу и бизнес-логику |
| Service/adapter | проверенные параметры, закрытые настройки | данные или результат операции | не зависит от оформления |
| View model | данные, контекст страницы | подготовленные props | не содержит секретов для браузера |
| Layout/page | props и список разделов | HTML документа | не выполняет скрытые бизнес-операции |
| Section/component | собственные props | локальная разметка | не зависит от случайных глобальных переменных |
| SCSS entry | модули страницы | CSS bundle | не импортирует все страницы без причины |
| JS entry | DOM и публичная config | экземпляры компонентов | одна точка владения init |
| Component | root/props/options | локальное состояние, события | cleanup своих ресурсов |
| Asset helper | manifest | URL файла | не знает локальный путь разработчика |
| Deploy | проверенный public build | опубликованный артефакт | не публикует исходную рабочую папку целиком |

```text
URL → entry → service/content → подготовленные данные → layout/page → HTML
                                                             ↓
asset manifest → helper → CSS entry + JS entry → компоненты браузера
                                                             ↓
                                  пользовательское действие → API/service
```

SCSS не читает PHP-конфигурацию во время работы браузера. Общий параметр передается через явно выбранный build/config-механизм. Сервер публикует только разрешенную браузеру часть настроек. JS изменяет собственное состояние, CSS описывает его представление.

## 5. Подключение SCSS без заданной сетки

Схема импортов страницы:

```text
entries/page-a.scss
  → project/                 значения этого сайта
  → base/                    общий фундамент
  → layout/page-a            каркас, разработанный под его макет
  → components/component-a   используемые компоненты
  → sections/section-a       используемые разделы
```

Пример только состава entry point:

```scss
@use "../base/document";
@use "../components/form";
@use "../sections/section-a";
```

Имена в примере обозначают будущие модули, а не уже существующие в репозитории файлы. В проекте создаются только нужные модули.

Интерфейсы SCSS-модуля:

- вход: явно подключенные tokens/functions/mixins;
- выход: селекторы своего компонента, локальные состояния, его media/container rules;
- соседние компоненты не изменяются побочными глобальными селекторами;
- значения и условия берутся из данного проекта, локальные исключения имеют владельца;
- entry point определяет состав и порядок каскада;
- изменение структуры импорта проверяется по выходному CSS на дубли и потерянные правила.

Состав колонок, размеры и пороги определяет конкретный макет. Иллюстрация mobile-first каскада с CSS-слоями приведена в [руководстве](05-PERFORMANCE-PLAYBOOK.md).

## 6. Связь адаптации с кодом

```text
условие проекта / компонента
  ├── CSS media/container query → изменение представления
  ├── JS matchMedia/наблюдатель → изменение поведения, если оно требуется
  └── правила resources         → подходящее изображение/модуль
```

Если одно условие используется в нескольких слоях, выбрать способ согласования: генерация из общего конфига, передаваемая публичная конфигурация либо другой документированный механизм. Наличие CSS custom properties само по себе не синхронизирует все условия CSS и JS.

Протокол смены режима:

```text
получить новое условие
→ если режим не изменился, не выполнять повторный init
→ сохранить значимое состояние
→ остановить ресурсы предыдущего режима
→ применить новый режим
→ восстановить допустимые состояние и фокус
→ проверить, что обработчики и запросы не продублировались
```

Это один и тот же технический контракт при любой сетке, числе колонок и диапазоне разрешений. Проверка выполняется на реальных условиях, выбранных для сайта, без наследования порогов референса.

## 7. Lifecycle и registry

```text
init(root, options)
  → проверить наличие обязательных узлов
  → предотвратить повторный init того же экземпляра
  → создать scope отмены / реестр disposer-функций
  → подключить поведение
  → включить enhanced-состояние после готовности
  → при ошибке cleanup и согласованный fallback

register(resource)
  → listener: AbortSignal / removeEventListener
  → observer: disconnect
  → timeout/rAF: cancel; выполненный handle убрать из реестра
  → request: AbortController + проверка актуальности ответа
  → animation: cancel / cleanup временного состояния

destroy()
  → повторный вызов безопасен
  → отменить ресурсы и восстановить нужные временные изменения
  → удалить регистрацию экземпляра

page registry / router / framework owner
  → создавать компоненты только для существующих roots
  → изолировать ошибку независимого init
  → владеть экземплярами и порядком teardown
  → учитывать переходы маршрутов, адаптивных режимов и bfcache
```

Это алгоритм, а не импортируемый готовый base class. Реализация выбирается под runtime; минифицированные классы референса не копируются как исходники.

## 8. Контракт загрузки

| Ресурс | Кто решает о подключении | Что проверить |
|---|---|---|
| CSS страницы | page config + asset helper | порядок каскада, только нужные зависимости |
| Общий JS | entry/registry | единичный init и разделяемое владение |
| Дополнительный JS | компонент или маршрут | условие загрузки, отмена, повторный вход |
| Изображения | HTML picture/srcset/sizes | реальный выбранный файл и отсутствие лишних запросов |
| Шрифты | font-face + страница | нужные диапазоны/начертания и fallback |
| Внешний сервис | adapter | ожидание, timeout, ошибка, альтернативный сценарий |

У каждого ресурса определены исходник, обработка, выходной путь, версия/хеш и потребитель. Основной контент и дополнительное улучшение различаются по требованиям к загрузке.

```text
Endpoint / method:
Поля, типы, длины и допустимые значения:
Авторизация / CSRF / origin / anti-abuse:
HTTP statuses и схема ответа:
Field errors / общая ошибка:
Deadline / отмена / retry / защита от дублей:
Что подтверждает success:
Adapter реальной доставки или внешней операции:
Логирование без чувствительных данных:

```

Клиент проверяет и статус, и схему ответа. Сервер самостоятельно проверяет входные данные. Отмена запроса не является успехом или обязательной сетевой ошибкой для пользователя.
