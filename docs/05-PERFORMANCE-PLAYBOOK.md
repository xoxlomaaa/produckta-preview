# Производительность с первого экрана

Версия 1.3. Применять вместе с [профилем проекта](templates/PROJECT-PROFILE.md) и [чек-листом релиза](04-RELEASE-CHECKLIST.md).

## 1. Выбор архитектуры

| Задача | Стартовый подход | Когда усложнять |
|---|---|---|
| Лендинг, портфолио, небольшой корпоративный сайт | HTML/SSG, CSS по маршруту, JS для отдельных интерактивных компонентов | Когда подтверждены требования к CMS, персонализации или сложному состоянию |
| Корпоративный сайт с редакторами | Готовый HTML из CMS, SSR или SSG. Кешировать публичные страницы по правилам платформы | Выделять персональные участки и динамические запросы по необходимости |
| Сервис или личный кабинет | Подобрать рендеринг и состояние по маршрутам. Публичные страницы и приложение могут иметь разные модели | Добавлять клиентский runtime там, где его оправдывает взаимодействие |

Первый экран, навигация и основной контент публичной страницы приходят в HTML и доступны сразу. Анимация и сложное поведение добавляются по мере загрузки. Подключение фреймворка, библиотеки или виджета обосновывается сценарием и проверяется по влиянию на код, сеть и основной поток.

## 2. CSS. Узкий экран как база

Для нового публичного сайта по умолчанию писать базовые правила для узкого контейнера. На широких экранах добавлять только необходимые изменения через `min-width` или container queries. Порог выбирать там, где контенту действительно требуется новая композиция. Для существующей CMS или дизайн-системы можно сохранить другую последовательную схему, описав её в профиле. [Адаптивная вёрстка](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/CSS_layout/Responsive_Design)

Пример для проекта, в котором нужны CSS-слои. Значения в примере иллюстративные.

```css
@layer reset, vendor, base, layout, components, utilities;

@layer components {
  .feature {
    display: grid;
    grid-template-columns: minmax(0, 1fr);
    gap: clamp(1rem, 3vw, 2rem);
  }

  @media (min-width: 48rem) {
    .feature {
      grid-template-columns: repeat(2, minmax(0, 1fr));
    }
  }
}
```

- Порядок слоёв объявляется в общем entry point. Внешние стили помещаются в согласованный слой, когда стек это позволяет. Обычное правило вне слоя выигрывает у обычного правила внутри слоя. Для `!important` порядок слоёв обратный. [Спецификация CSS Cascade Layers](https://www.w3.org/TR/css-cascade-5/#layer-order)
- Базовые правила и расширения лежат у владельца компонента. DOM, чтение и фокус организованы в логическом порядке. Смена сетки по ширине сохраняет доступ к содержимому.
- Один компактный stylesheet для маршрута — хороший старт. Отдельный desktop-файл или critical CSS оправданы, когда измерения показывают пользу. Media query определяет применение CSS, а браузер может скачать stylesheet с несовпавшим `media` с меньшим приоритетом. По Network проверять, какие ресурсы действительно переданы. [Media queries и загрузка стилей](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Media_queries/Using)

## 3. Изображения. Формат под материал

| Материал | Что сравнить |
|---|---|
| Фотография, рендер, крупная иллюстрация | WebP и AVIF при одинаковых размерах и сопоставимом визуальном качестве. JPEG оставить как вариант, когда он выигрывает по условиям проекта или нужен для совместимости. |
| Скриншот с мелким текстом, резкие границы, прозрачность | Lossless WebP и PNG. Проверить читаемость и края в реальном размере. Для фотографического выреза можно сравнить lossy WebP с прозрачностью. |
| Логотип, иконка, контурный рисунок | Оптимизированный SVG из доверенного источника с сохранением вида и правильным доступным именем по месту использования. |

Проверять кандидаты на одинаковом кадрировании и размере, сравнивать переданные байты и визуальные артефакты. Для крупных изображений отдельно смотреть декодирование и влияние на LCP на целевом устройстве. Исходники хранить отдельно от сжатых производных. [Форматы и варианты изображений](https://web.dev/learn/performance/image-performance)

- Формировать разумное число ширин по реальным размерам блока. `srcset` описывает доступные файлы, `sizes` — ширину изображения в макете. `picture` подходит для выбора формата или разного кадрирования. Порядок `source` важен: браузер берёт первый подходящий.
- Для альтернативного кадрирования резервировать правильное соотношение сторон в каждом режиме. Указывать размеры в HTML там, где они соответствуют выбранному кадру. Это снижает сдвиги при загрузке.
- Если LCP — изображение, дать браузеру обнаружить его в исходном HTML. Оставить обычную загрузку и при подтверждённой необходимости дать `fetchpriority="high"`. Preload применять только при необходимости и проверять отсутствие двойного запроса. Для изображений ниже экрана использовать `loading="lazy"` по назначению. [Оптимизация LCP](https://web.dev/articles/optimize-lcp)
- В Network подтвердить выбор файла на узком и широком экране. Считать фактически загруженные варианты, включая фон, постер, первый кадр видео и дубли.

Пример для фотографии с пропорциями 3:2. В этой условной раскладке изображение занимает весь viewport на узких экранах и половину на широких. Для реального блока `sizes` сверяется с его CSS.

```html
<picture>
  <source type="image/webp"
    srcset="/images/scene-480.webp 480w, /images/scene-960.webp 960w"
    sizes="(min-width: 64rem) 50vw, 100vw">
  <img src="/images/scene-960.jpg"
    srcset="/images/scene-480.jpg 480w, /images/scene-960.jpg 960w"
    sizes="(min-width: 64rem) 50vw, 100vw"
    width="960" height="640" alt="Витрина магазина с каталогом товаров">
</picture>
```

## 4. Шрифты, JavaScript, анимация и доставка

- **Шрифты.** Для локальных веб-шрифтов использовать лицензированный WOFF2. Ограничить число начертаний и сохранить нужную кириллицу, цифры и знаки. Выбрать `font-display` под сценарий и проверить смену шрифта. При сдвиге сверить метрики fallback. Предзагружать только шрифт, который доказанно нужен для первого экрана.
- **JS.** Подключать код по маршруту и потребности компонента. Тяжёлый необязательный код подгружать рядом с местом применения, если это улучшает измерения. Проверить, что пользователь может читать страницу, переходить по ссылкам и получить понятное состояние при отказе дополнений.
- **Анимация.** Статический кадр доступен с первого рендера. Основное движение строится на `transform` и `opacity`, когда это подходит сцене. Эффекты с перерисовкой проверять в Performance. Статическая версия для reduced motion передаёт тот же смысл. Длительные сцены останавливаются вне области просмотра, если продолжают расходовать ресурсы. [Производительность анимаций](https://web.dev/articles/animations-guide)
- **Третьи стороны.** У виджета или аналитики есть владелец, цель, условие запуска и стоимость в бюджете. Для тяжёлого необязательного embed подходит постер с загрузкой по действию. Приёмка охватывает публичную конфигурацию и состояние после запуска интеграций.
- **Хостинг.** Проверять HTTPS, Brotli/Gzip для текстовых файлов, MIME, время ответа HTML и заголовки кеша на опубликованной сборке. Долгий immutable-кеш предназначен для файлов с хешем или другой гарантированной версией в URL. HTML и персональные ответы имеют отдельные правила. Отдельно проверять холодную и повторную навигацию.

## 5. Бюджеты до старта

Пример начального бюджета для лёгкого публичного лендинга. Значения корректируются по пилотной сборке и записываются в профиль. КиБ — переданные байты тел HTTP-ответов, с учётом сжатия доставки. Для JS дополнительно учитывать размер после распаковки и время исполнения.

| Ресурс | Пример лимита |
|---|---:|
| HTML | 25 КиБ |
| CSS для начальной загрузки | 35 КиБ |
| JavaScript для начальной загрузки, включая третьи стороны | 30 КиБ |
| Шрифты начального экрана | 80 КиБ |
| Изображение первого экрана, если используется | 130 КиБ |
| Все ресурсы начальной загрузки | 350 КиБ |

В профиле указать одинаковое для повторов окно наблюдения и режим кеша. Например, холодный старт без прокрутки до 5 секунд от начала навигации с учётом ресурсов, запрошенных в этом окне. Отдельно измерять полный проход по странице, первый клик и вес отложенных сцен. Порог по байтам дополняется метриками браузера и ручной проверкой.

## 6. Как измерять и принимать

1. Выбрать репрезентативные маршруты. Главная, типовая внутренняя страница и страница или сценарий с тяжёлым компонентом, если они есть.
2. Запускать один и тот же production build. Записать commit, URL, версии Chrome/Lighthouse, профили mobile/desktop, параметры эмуляции, режим кеша и состояние интеграций. Сравнивать результаты в сопоставимой среде.
3. Сделать по 3–5 прогонов на сочетание маршрута и профиля. Хранить медианы и разброс оценок и метрик. Результат 100 отмечать с маршрутом, категорией и условиями. Если есть Lighthouse CI, хранить отчёты и проверять согласованные пороги. [Настройка Lighthouse CI](https://github.com/GoogleChrome/lighthouse-ci/blob/main/docs/configuration.md) · [Почему меняется оценка Lighthouse](https://developer.chrome.com/docs/lighthouse/performance/performance-scoring)
4. В автоматических проверках в первую очередь блокировать воспроизводимые проблемы: превышение бюджета, ошибку сборки, сломанную навигацию, подтверждённую регрессию доступности или ключевого сценария. Шумные метрики сравнивать по серии прогонов. Лабораторно смотреть LCP, CLS и TBT. INP проверять отдельно по реальным взаимодействиям, когда появятся полевые данные.
5. Вручную пройти ключевой путь мышью, касанием и клавиатурой, проверить фокус, ошибки формы, масштабирование, режим уменьшенного движения и реальные переходы между ширинами. Для контента с вертикальной прокруткой ориентир WCAG AA по reflow — ширина, эквивалентная 320 CSS px, с оговорёнными стандартом исключениями. [Lighthouse Accessibility](https://developer.chrome.com/docs/lighthouse/accessibility/scoring) · [WCAG Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)
6. После публикации смотреть полевые CWV на 75-м перцентиле раздельно для mobile и desktop. Цели — LCP ≤ 2,5 с, INP ≤ 200 мс, CLS ≤ 0,1. Если трафика недостаточно, указать, что полевые данные пока недоступны. [Core Web Vitals](https://web.dev/articles/vitals)

100/100 — целевая оценка Lighthouse. Готовность релиза определяется по совокупности результатов. Проверки Accessibility, Best Practices и SEO дополняются [порядком технической приёмки](06-SEO-AND-RELEASE.md).
