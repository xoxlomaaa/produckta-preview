# Техническое SEO и выпуск сайта

Версия 1.3. Использовать с [профилем проекта](templates/PROJECT-PROFILE.md), [руководством по производительности](05-PERFORMANCE-PLAYBOOK.md) и [чек-листом релиза](04-RELEASE-CHECKLIST.md).

## 1. До вёрстки. Карта страниц и адресов

Определить основной домен, протокол, правила адресов и поведение параметров. Для каждого типа страницы записать назначение, URL, модель рендеринга, источник метаданных и режим индексации. Для маленького сайта хватит таблицы в профиле, для каталога правила лучше задавать по типу маршрута. Главная, услуги, публикации, фильтры и служебные страницы могут иметь разные правила.

| Тип URL | Ожидаемое поведение |
|---|---|
| Публичная самостоятельная страница | HTTP 200, доступный основной контент, предпочтительный URL в canonical, переход по обычной ссылке. |
| Дубль или параметр отслеживания | Согласовать canonical и внутренние ссылки с основным URL. Параметры, которые меняют содержание, разобрать отдельно. |
| Страница переехала | Постоянный редирект 301 или 308 на релевантную замену. Обновить внутренние ссылки и карту сайта. |
| Страница удалена без замены | HTTP 404 или 410 и понятная страница для посетителя. |
| Приватная страница или закрытый предпросмотр | Контроль доступа на стороне сервера или хостинга. |
| Публичная служебная страница вне поиска | `noindex`, если URL должен оставаться доступным посетителю и поисковому роботу для чтения директивы. |

Canonical, внутренние ссылки, редиректы и sitemap согласуются. Для canonical и sitemap использовать абсолютные публичные URL. При переезде проверить исходный и конечный адреса, цепочки, циклы и фактический HTTP-статус. [Канонические адреса Google](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls) · [Канонические адреса Яндекса](https://yandex.ru/support/webmaster/ru/robot-workings/canonical) · [HTTP-статусы и обход](https://developers.google.com/crawling/docs/troubleshooting/http-status-codes)

## 2. Контракт индексируемой страницы

- Осмысленные `title` и `description` для каждого типа страниц. Заголовки, текст, ссылки и изображения объясняют содержание. Для повторяемых страниц значения формируются из реальных данных по шаблону с понятным fallback.
- Основной контент и навигация доступны на мобильной версии. Для публичных страниц предпочтителен готовый HTML. Если контент рендерится на клиенте, проверить итоговый HTML в инструменте инспекции. Основной текст и ссылки должны появляться без клика, прокрутки или входа.
- Ссылки оформляются как `<a href="…">`. Важные страницы доступны из навигации, каталога или связанных страниц. Осмысленные изображения получают контекстный `alt`, декоративные — пустой `alt`.
- Превью для соцсетей добавлять по задаче проекта и проверять отдельно. `hreflang` нужен для реальных языковых или региональных версий. Проверить взаимные ссылки и согласованность с canonical.
- Структурированные данные добавлять там, где есть применимый тип и видимый контент. Проверять поддерживаемые типы в Rich Results Test, а общую разметку Schema.org — в соответствующем валидаторе. Корректная разметка даёт возможность попасть в расширенный результат. [SEO Starter Guide](https://developers.google.com/search/docs/fundamentals/seo-starter-guide) · [Mobile-first indexing](https://developers.google.com/search/docs/crawling-indexing/mobile/mobile-sites-mobile-first-indexing) · [Структурированные данные](https://developers.google.com/search/docs/appearance/structured-data/sd-policies)

## 3. Индексация и окружения

- Генерировать `sitemap.xml` из фактических индексируемых канонических URL со статусом 200. Исключать предпросмотры, редиректы и `noindex`. `lastmod` указывать при наличии надёжной даты существенного изменения.
- `robots.txt` управляет обходом. Для исключения публичной страницы из индекса использовать `noindex` в метатеге или HTTP-заголовке и оставить роботу возможность его прочитать. Приватные данные защищаются контролем доступа.
- На релизе проверять фактические заголовки и HTML production. У публичных страниц должны быть корректные canonical, разрешённый обход и индексируемый контент. У предпросмотра — правила по его назначению.
- После публикации, при доступе к кабинетам, подтвердить домен, проверить карту сайта и несколько живых URL в Google Search Console и Яндекс Вебмастере по целевым рынкам. Зафиксировать отправку, результаты инспекции и владельца наблюдения. Обход, индексация и позиции отслеживаются отдельно. [Требования Google](https://developers.google.com/search/docs/essentials/technical) · [Карта сайта Google](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap) · [Карта сайта Яндекса](https://yandex.ru/support/webmaster/ru/controlling-robot/sitemap)

## 4. Хостинг и приёмка релиза

1. **Сборка и окружение.** Воспроизвести чистую production-сборку по README. Проверить HTTPS и сертификат, перенаправление на основной origin, отсутствие смешанного контента, MIME, сжатие и кеширование. Проверить доставку ресурсов с реального домена и подкаталога, если он используется.
2. **Данные и интеграции.** Закрытые настройки хранятся на сервере. У формы проверить реальную обработку тестовой заявки в разрешённой среде, валидацию, состояния ошибки и повторной отправки. В логах и отчётах исключать чувствительные данные. Аналитику и другие интеграции проверять в той конфигурации, с которой их получит посетитель.
3. **Совместимость.** Пройти ключевые сценарии на согласованной матрице браузеров и устройств, включая узкий экран, клавиатуру и режим уменьшенного движения. Проверить URL напрямую, возврат назад и полезное состояние при отказе необязательных ресурсов.
4. **Проверки и выпуск.** До релиза проверить статус-матрицу и обязательные метаданные на репрезентативных маршрутах. После релиза повторить проверку на публичном домене. Указать ответственного, место отчётов, контрольные URL и процедуру отката. В CI автоматизировать проверки, которые дают воспроизводимый результат.

## 5. Что проверять по четырём категориям Lighthouse

| Категория | Что проверяем сверх балла |
|---|---|
| **Performance** | Серия mobile/desktop замеров, вес ресурсов, прокрутка, первый клик, LCP/CLS/TBT в лаборатории и полевые Core Web Vitals при наличии данных. |
| **Accessibility** | Ручной проход клавиатурой, видимый фокус, чтение формы и ошибок, контраст, масштабирование и уменьшенное движение. Если требуется соответствие WCAG, оценивается отдельно по выбранному уровню. |
| **Best Practices** | HTTPS, смешанный контент, ошибки консоли и загрузки ресурсов, состояние зависимостей и корректная работа сторонних интеграций. |
| **SEO** | Статусы, canonical, robots, sitemap, доступность основного контента и проверка опубликованного URL в инструментах поисковиков. |

Цель 100/100 относится к согласованным страницам, версиям Lighthouse и профилям. Порог приёмки и бюджет задаются в проекте. Оценку 100 фиксируют как результат конкретного прогона. Техническое SEO, ручная доступность и устойчивость в реальных условиях оцениваются отдельно. [Категории Lighthouse](https://developer.chrome.com/docs/lighthouse/overview) · [Оценка доступности](https://developer.chrome.com/docs/lighthouse/accessibility/scoring)
